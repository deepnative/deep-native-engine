# Deliver an authorized issue

Follow the [local verification playbook](../../../assets/docs/workflows/LOCAL-VERIFICATION-PLAYBOOK.md); all tests run locally and Actions only deploys to Azure.

Before delivery work, follow [issue coordination](../../../assets/docs/workflows/ISSUE-COORDINATION.md): verify existing ownership, publish the assignee/worker/scope/branch claim, set `status:in-progress` and project In progress, then re-read for competing claims. Keep review/blocker status current and release or hand off the claim at task completion; partial issue delivery stays open.

Follow the shared BDD procedure in the team workflow: use the issue scenarios to write a meaningful failing behavioral test before missing behavior, then implement and record passing evidence. Map scenario IDs to actual tests and approved journey IDs where applicable; preserve all existing gates. Do not fabricate failures for already delivered behavior or add a runner just for Gherkin prose.

1. Read [AGENTS.md](../../../AGENTS.md), the live issue, [team workflow](../../../assets/docs/workflows/TEAM-WORKFLOW.md), the [current product direction](../../../assets/docs/PRODUCT-DIRECTION.md), and applicable historical source context. Exercise audience-dependent behavior with IT, non-IT professional and general-learner examples; do not make paid coaching or contracting a universal prerequisite. Confirm scope and dependencies against evidence. Stop only dependent work if blocked; an issue or historical prompt alone is not permission to implement.
2. Inspect branch, dirty state, existing code and tests. Preserve unrelated edits; use a suitable isolated Git worktree with a `codex/` branch for every new implementation or repository edit, keeping the primary checkout out of delivery editing. Record the actual worker/tool, unique claim ID, owned files/scope, branch and worktree path; preserve other workers' claims, branches, worktrees and live gate processes. Serialize full gates and continue observing the same confirmed process after a timeout; do not restart it or treat a timeout as a result. Select the model from current issue labels and obtain separate Astra design when requested. Record invariants before critical changes.
3. Establish a focused behavioral baseline using the playbook; no automatic full baseline is required. Define tests from AC, reproduce bugs first, then make the smallest complete change. Inspect affected callers, fixtures and provisional journeys; keep focused output separate from acceptance artifacts and use owned native/browser resources. Include failures, recovery, isolation and boundaries; use synthetic data. Check current official APIs and pinned dependency/license choices when adding dependencies.
4. Follow [the verification contract](../../../assets/docs/workflows/VERIFICATION.md). The shared entry point includes QA-001/002/003 checks for the initial learning slice. Preserve these checks and extend the scenario register for every authorized feature; a partial slice cannot satisfy full-MVP gates. Never weaken source inclusion, scenario denominators, thresholds, or tests to pass.
5. Finish affected checks, documentation and source self-review, then commit only intended files. Run the complete `make verify` on that final clean push candidate, inspect original results and use the ordinary receipt-aware push. Do not add an automatic second campaign for unchanged push/review/handoff; a new commit or invalid proof requires fresh verification. Never bypass the hook. Record a self-review of the new revision, issue AC and actual evidence; verify exact local proof for the new revision, and use a separate reviewer when explicitly requested or actually required. Never call self-review independent.
6. Complete the merge-to-main procedure in the team workflow under the owner's standing authorization. Review the current head/base, resolve blockers, satisfy actual required reviews/protections and successful local proof, mark the PR ready, merge promptly with the expected head SHA, and verify the resulting main tree and parents against the tested source. Then clean up that merged PR's remote/local branch and clean isolated worktree after the workflow's ownership, tip and dirty-state checks; record a blocker when unsafe. Do not wait only for an optional reviewer or model-review label. Respect an explicit draft-only/review-only request and never bypass protections; do not ask for authorization already provided.
7. Return changed behavior, AC evidence, commands/results, PR and merge SHAs, resulting-main source/parent verification, and unresolved gaps using the [evidence template](../../../assets/docs/templates/EVIDENCE.md). Name one next bounded issue or owner decision, why it is next, dependencies/claims, and its recommended lead model/starting effort from live labels; separate design/review settings when relevant. A recommendation does not claim or authorize the next issue. Do not present self-review or synthetic tests as independent proof of sensitive or live work, close unmet issues, or launch beyond authorization.

After verified-main product delivery, show the actual changed journey using [the milestone demo procedure](../../../assets/docs/workflows/MILESTONE-DEMOS.md), recording revision/date, environment/provider state, observed actions/outcomes, access/restart instructions, useful captures and limitations. Update the concise product README for delivered capabilities. Use a dedicated invented-data preview, never an active quality-gate database/server; keep credentials/private member files out of captures and links. Documentation/tooling work shows the changed artifact. If access is unavailable, record its blocker and next action. This does not replace verification/cleanup, authorize deployment, or establish broad-parent, qualified or full-MVP acceptance.
