# AI, put to practice — complete local foundation reader

This reader makes all six authored lessons and the connected final practice usable in Everyday, Work and Technical routes. It is a local learning experiment under [#549](https://github.com/deepnative/deep-native-engine/issues/549), separate from the shared application reader owned in #117.

Choose a route, then follow **example → try → fresh case → your work**. Practice choices and claim classifications have hints and source-based explanations. Incorrect answers invite revision; correct responses lead to a fresh case. Questions include the drafts or schedules they ask the learner to inspect. The reference panel follows the fresh exercise's source. During later own-work stages, it shows the learner's Lesson 1 notes as **Your starting work**, with an instruction to check the original source; without those notes it offers a labelled example. The final practice has four freely navigable steps: **read the brief → write a first draft → read the update → revise and check**. The first five writing fields stay together; the sixth keeps a separate revision. Each field shows its existing numbered instruction; the case’s expected output appears above the first draft. A collapsible source reminder and retained first draft remain available. See the [workflow and evidence](guided-final-practice.md).

Opening a page is not completion. The path distinguishes written notes and a deliberate learner self-check. Editing fresh writing, lesson work or the final record clears the applicable previous self-check. Free writing has authored criteria and comparisons, not an automatic grade. Comparisons are supplied examples rather than responses generated from the learner's text.

Lesson 2's **Fresh case** adds [three supplied follow-up conversations](../study-dialogues.md). Keep an initial request, try the hint, then retain a repair and a reason in the existing writing field. Separate disclosures show the worked repair and how to handle missing evidence or unsupported requests. Opening them never replaces the writing.

Lesson 6's **Fresh case** now includes a [feedback decision workspace](feedback-workflow.md). Learners can revise, decline with a reason or record an already-addressed change while preserving draft/comment versions. Decisions and unfinished responses use the same explicit notebook save and export. A clarification stays in the notebook; it is not sent to a reviewer.

**Put it all together** also offers [Shape a contribution](../contribution-practice.md). Read the fictional workflow, keep a first proposal, compare supplied editorial feedback, and record a revision with its reason. Intended attribution/audience is only a future plan; cancelling it retains the private draft. The optional proposal self-check is separate from the six-step record. No contribution is required to finish that record.

The Work final practice now uses [CAP-W2: a changing handover pilot](../realistic-work-practice.md). Write a short team update from three dated notes, calculate whether the workload fits, propose a feasible option, then open a later decision and keep your revision/reason separately. A five-case and a six-case proposal can both be defensible; the rubric checks evidence, tradeoffs and arithmetic. The complete packet is included in notebook downloads. The earlier simpler Work case remains in `foundation-practice.md`; earlier notebook bytes stay separate.

The Technical final practice uses [CAP-T2: an upload-bug investigation](../realistic-technical-practice.md). Reconcile obsolete/current requirements, a vague report, a specific UI failure, a successful control and an interrupted attempt. Produce an investigation and boundary test plan, then revise after a new JPEG requirement and an unverified patch proposal. Supplied observations, hypotheses and planned runs stay distinct. Downloads retain the full packet; the earlier simpler Technical source remains in `foundation-practice.md`.

The Everyday final practice uses [CAP-E2: the book swap](../realistic-everyday-practice.md). Correct an old invitation, count guests/helpers/waitlist separately and choose a feasible table/holding-box plan. A later reply snapshot changes confirmed and reserved places. Learners can retain correct reminder wording while revising the checklist and reason. The complete packet is downloadable; earlier Everyday source/notebooks stay separate.

## Run locally

Use the already running dedicated content-preview server when available; its address is recorded in the #549 handoff. It serves only `assets/docs/learning-design` and has no database, provider or member account. From the repository root, if no suitable preview is running:

```sh
python3 -m http.server 0 --bind 127.0.0.1 --directory assets/docs/learning-design
```

Open `http://127.0.0.1:<printed-port>/reader/`. Keep that process running; do not use the application's shared gate port. Reuse the same host and port to revisit browser saves. The earlier [request/check walkthrough](../prototype/README.md) remains available at `/prototype/` on the same server.

**Save in this browser** explicitly stores this route's current lesson/stage and final-practice step, responses, notes, the optional contribution and self-checks at this origin. Switching routes preserves separate in-page drafts; reloading restores only explicit saves. Each content hash has a separate key under `dne-course-reader-1:<route>:<hash>`. Compatible records without the optional contribution open with an empty worksheet. A record without a final-practice step opens at the brief, keeping all writing/checks; this default is only in memory until explicit save. Invalid stage data protects the original stored copy; new saves use the versioned key. The earlier prototype's storage is unchanged. There is no account save, server submission or reviewer exchange. Use invented information, especially on a shared browser.

**Download my work** keeps a text copy of the current route's sources and writing, including when saving fails. **Earlier notebooks** preserves and downloads previous stored records; their answers and self-checks are never automatically moved to new content. A readable earlier-content record does not block a separate current save, even if its answer options no longer exist. A malformed current record or unreadable original save remains protected from overwrite and separately downloadable. Earlier raw downloads include the stored version identifier and writing, not a complete old-lesson archive. There is no automatic migration, import or deletion tool.

## Refine and verify

Eleven authored Markdown files and `feedback-cases.json` are the sources. `build.py` extracts route-specific content, verifies the structured feedback sources/comments against Lesson 6 and generates `course.mjs`, including all twelve source hashes. It uses Python's standard library and supports the Markdown forms in these drafts; it is not a general renderer for external or member content. Authored changes create a new content hash and keep previous notebooks separate. The guided-layout change preserves all twelve source hashes and the current content hash; it adds generated presentation sections without changing the existing instructions or source packets. Field guidance is extracted from those numbered instructions, with validation that fields 1–5 and the later revision instruction remain present and ordered. The complete instructions are visible beside the fields, replacing the whole-task disclosure.

```sh
python3 assets/docs/learning-design/reader/build.py
python3 assets/docs/learning-design/reader/build.py --check
node assets/docs/learning-design/reader/checks.mjs <reader-url> <evidence-directory>
```

Use the repository's installed Node 24+ and Playwright. The browser runner uses fresh Chromium contexts at 1360 × 950 and 390 × 950, without the application database or shared port. Add `--case READER-009`, for example, to reproduce source-switch checks. Its reports and screenshots are local-reader evidence, not the full application matrix.
