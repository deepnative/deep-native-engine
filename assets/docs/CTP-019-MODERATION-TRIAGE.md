# CTP-019: private synthetic moderation triage

This bounded local slice implements [#192](https://github.com/deepnative/deep-native-engine/issues/192) under the still-open [CTP-019 #39](https://github.com/deepnative/deep-native-engine/issues/39). The existing private member-proposal queue remains the only source. It does not read assignment evidence, paid-service requests, support notes, bookings or expert availability. No real moderation staffing, response target, qualified review, license or publication is claimed.

The queue's SQL statement checks the current moderator or platform-admin role and active principal token before returning submitted or quarantined proposals. It orders by `submitted_at` and proposal ID, then caps results at 100. This uses the time the member actually submitted, rather than draft creation time; the ID gives stable ordering for ties. The page shows the UTC submission time and a nonnegative elapsed minute count computed at page load. At 100 visible items it says more may exist; it does not claim a complete count. Actions still perform their own current-role and state checks. Withdrawal or rejection redacts text, and a stale action cannot restore it.

The follow-up [#367](https://github.com/deepnative/deep-native-engine/issues/367) adds continuation between bounded 100-candidate windows. Its opaque signed cursor carries the database's exact submission timestamp and proposal ID, and is bound to the current staff actor and session. A different session, actor or store instance cannot reuse it. Restarting this local store invalidates old links; the moderator can return to the first page. Each request checks the actor's current permitted role and PostgreSQL wall-clock session expiry, preserves principal/workspace/proposal lock order, writes a content-free `proposal_read` event for every returned item, and commits those events before returning private text. Candidate IDs and ordering keys are selected before row locks; removed candidates are never refilled from an unlocked window. The next cursor advances from the last selected candidate even if that candidate is later withdrawn or deleted.

The worklist changes while it is browsed. New submissions with ordering keys after the current cursor may appear later; earlier keys require returning to the start. A full page can offer a next link that leads to an empty page because the query does not read an unaudited 101st item to predict whether more exists. No total or immutable snapshot is claimed. Continuation changes no proposal state, action permission, retention rule or publication path.

Only invented/sample information should be used in this local preview. An authorized moderator can already read submitted sample text; these slices do not widen that permission. The page remains uncached. No migration or new retained data exists. Community report moderation, live review/booking work, allowances and support operations remain separately tracked in #193–#196.
