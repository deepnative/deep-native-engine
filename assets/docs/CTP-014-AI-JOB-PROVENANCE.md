# Synthetic AI job provenance

This is the internal job-state slice of [CTP-014 #31](https://github.com/deepnative/deep-native-engine/issues/31), tracked by [#186](https://github.com/deepnative/deep-native-engine/issues/186). It extends the ambiguity fence in [#184](https://github.com/deepnative/deep-native-engine/issues/184). No member-facing AI route or live provider is connected.

New demo/test AI jobs require a bounded prompt-template version and model-contract version. They are immutable for the job's idempotency key: exact replay returns the same job, while changed versions or request input conflict. These are internal contract identifiers, not a provider allowlist or evidence of model approval. The caller must use reviewed constants rather than member-supplied version strings.

After validating a simulated adapter result, the worker stores only its opaque operation reference in the same conditional PostgreSQL transition that marks the active attempt succeeded. A failed or held attempt does not acquire a reference. A stale attempt token cannot overwrite a successful job or turn a held job into success. Invalid or oversized identifiers and references are rejected; raw request input, prompt body, provider response, exception text and credentials are not stored in job rows. This syntactic check alone would not prove a future provider's reference is semantically opaque; a live provider contract must establish that separately.

Migration 020 adds nullable metadata columns and constraints. Existing AI jobs remain readable with null provenance, and existing non-AI jobs keep null metadata. A versioned AI job cannot be marked succeeded without a reference. The migration is forward-only and repeatable through `schema_migrations`; it does not fabricate historical provider IDs or versions. Rollback requires stopping workers and preserving any versioned rows before reverting the schema, because earlier code cannot interpret the new columns or their idempotency meaning.

Consent, member/source ownership, token and cost reservation, kill switch, held-job reconciliation, provider/model policy and full-MVP browser acceptance remain open under #187–#190. This internal metadata must never be used to infer permission to dispatch private evidence or spend an allowance. No approved browser journey changes in this slice; the local and full-MVP registers remain separate.
