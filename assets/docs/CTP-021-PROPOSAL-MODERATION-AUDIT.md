# CTP-021: local private-proposal moderation audit

This implements the bounded local privacy control in [#339](https://github.com/deepnative/deep-native-engine/issues/339), under parent [CTP-021 #40](https://github.com/deepnative/deep-native-engine/issues/40). It does not establish contribution publication, a license, qualified moderation coverage, hosted retention, or full-MVP acceptance.

## Behavior and invariants

Every successful moderator/admin queue invocation commits one `proposal_read` event for each returned proposal before any private text leaves the store. An empty queue adds no event. Submitted-to-quarantined, submitted-to-rejected, and quarantined-to-rejected transitions append one event in the same transaction as the state change. Rejection still nulls title, body, sources and workflow reference. A redirected GET after moderation is a separate queue invocation with its own read events. Denied, invalid, stale and repeated transitions add no successful-transition event.

The `proposal_audit` schema contains only an event ID, actor UUID and controlled role, actual owning workspace/member UUIDs, proposal UUID, controlled action and old/new states, and server timestamp. It has no private content, URL, workflow reference, token/hash, cookie, CSRF value, filename, reason or capability fields. The workspace/member composite foreign key validates actual ownership, including workspaces whose UUID differs from their member's UUID. Historical actor/proposal identifiers deliberately do not cascade on withdrawal, redaction or staff changes. Updates and deletes are rejected while the owning workspace exists; local workspace deletion cascades only that workspace's events.

## Transaction and ordering decision

The common moderation transaction locks, in order:

1. The current staff principal with `FOR SHARE`, validating token, kind, revocation and wall-clock expiry.
2. Its current moderator/admin profile with `FOR SHARE`, so a role change must win before the read or wait until after it commits.
3. Candidate member principals in UUID order, then their non-deleting workspaces in UUID order, both `FOR SHARE`.
4. Eligible proposal rows in UUID order with `FOR UPDATE`, retained until commit. The materialized locked subquery returns them in the existing submission-time/UUID order.

Member principal locks precede workspaces and proposals because local member deletion starts by deleting the principal and may cascade through learner/proposal rows before workspace rows. This prevents a deletion cycle where one transaction owns the workspace and waits for a proposal while the other owns the proposal and waits for its workspace. Concurrent queues use the same proposal order. Queue reads intentionally serialize on their bounded proposal rows with moderation and withdrawal; no lock upgrades are required.

The initial candidate selection contains identifiers only, excludes already absent/deleting workspaces before applying the limit, and preserves the existing 100-item window. This keeps a failed local deletion cleanup from filling the oldest window indefinitely and hiding eligible proposals. A candidate withdrawn or deleted before its locks are acquired is omitted; this invocation does not refill the window with an unlocked later proposal. No private fields are selected until ownership/state locks are held. Workspace deletion marking denies later access. Locks order revocation, role changes, withdrawal, member deletion, and audit/transition commits; they cannot recall content already delivered by a committed read.

A final `clock_timestamp()` check after lock acquisition and audit writes prevents transaction-start timestamps or expired authorization after waits from authorizing output. Expiry is checked immediately before COMMIT; future expiry cannot retroactively retract an already committed read. Insert or deferred-constraint COMMIT failure propagates through the existing safe HTTP 503 response, withholds text/success and rolls back the whole event batch or transition. If rollback also fails, the pool connection is discarded. No new endpoint or moderation privilege is added.

## Migration and rollback

Migration 038 adds the proposal-specific table, ownership FK, controlled-state constraints, index and append-only trigger. Existing authorization audit tables/events are untouched, and no historical proposal access is inferred. It is registered in the existing migration list and can be applied again without changing events.

A local application rollback must keep this additive table and its history. Reverting to an application version without these writes would resume unaudited moderation and is not an acceptable privacy rollback: disable moderation while repairing forward. Do not drop events or weaken immutability to make an older application appear compliant. Hosted backup/retention remains outside this local slice.
