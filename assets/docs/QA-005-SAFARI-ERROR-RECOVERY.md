# Exercise error-link typing recovery

This bounded [#109](https://github.com/deepnative/deep-native-engine/issues/109) change addresses its keyboard/error-recovery acceptance criteria. In the retained native Safari control, activating an exercise error link showed textarea focus, but immediate keyboard input did not enter the field. Selecting all first was an observed workaround. Focus appearance alone was insufficient evidence that editing worked.

The exercise error summary now loads a small progressive browser module. Ordinary activation focuses the named field and establishes a textarea caret after its existing text. It does not replace the text, check confirmation, submit, store or transmit anything. Modified/nonprimary clicks, already-handled clicks and missing targets retain their ordinary behavior. The server-rendered POST form and fragment links remain present without JavaScript; no disabled-JavaScript browser result is claimed here.

The module uses the documented [focus API](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/focus) and [textarea selection API](https://developer.mozilla.org/en-US/docs/Web/API/HTMLTextAreaElement/setSelectionRange), checked on 16 October 2026. There is no dependency, provider, schema, authorization or CSP change. All first-party browser JavaScript remains included in per-module and global coverage.

## Blocking PostgreSQL fixture observation

The first clean full gate at `e810f5e7e8257f876aab6e19bed5bde976633746` failed an existing `practice-withdrawal.test.ts` rollback-discard check: **2,355/2,356** native tests passed. Its immediate principal `FOR UPDATE NOWAIT` encountered a retained lock. The browser/provisional/audit stages were not reached. This failure remains retained, separate from focused Safari evidence.

A controlled native observation on unchanged application code reproduced the ordering issue: the application requested discard and the pool's local count became zero while the exact PostgreSQL backend still existed and held its lock. After the same ordinary native close completed, the backend disappeared, both original NOWAIT probes passed and the prior response/null-withdrawal facts remained intact. This proves the ordering race can occur; the original failed run did not capture that connection's close timing, so it is not retrospective proof of every failure's cause. The [node-postgres API](https://node-postgres.com/apis/pool) and pinned driver implementation distinguish local release from native closure.

The [bounded scope extension](https://github.com/deepnative/deep-native-engine/issues/109#issuecomment-6219507535) maps **QA109-GATE01** to #109 AC4 and the existing #353 failed-rollback-discard contract. The same test now checks the actual discard argument, positive backend PID and local removal, then observes that exact backend's absence before executing both unchanged NOWAIT probes and the unchanged stored-data assertions. Its 3,000ms lifecycle observation stays inside the unchanged 5,000ms native-test deadline. It polls lifecycle state, never retries a member mutation or failed lock assertion, and never calls `pool.end()` before these assertions to manufacture cleanup. No runtime practice/authorization/redaction code changes.

The corrected full native file passed **22/22** cases on fresh isolated PostgreSQL. **QA109-GATE02** deliberately omitted the discard argument in a separate source copy: the same file produced **21 passes and exactly one expected failure** at the failed-rollback test's discard assertion. The application source in the delivery checkout remained unchanged. Both executions had zero skips and ordinarily removed their owned databases with absence confirmed. An initial TypeScript check caught a nullable typed SQL row access; its guaranteed single-row non-null annotation was corrected, types/lint passed, and the final typed candidate's native file passed 22/22. These are scoped fixture results, not a full-gate pass.
