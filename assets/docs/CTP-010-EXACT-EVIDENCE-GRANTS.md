# CTP-010 synthetic exact evidence grants

For local synthetic evidence, a current platform administrator may grant one current reviewer access to one queued or reviewed submission object under one current reviewer workspace assignment. Migration 022 stores the exact assignment and submission IDs, purpose, expiry, revocation and grant issuer. The object remains member owned. Upload, scan and private-review consent do not grant reviewer access by themselves.

Every download-link request and capability replay rechecks the reviewer principal, exact assignment, exact object grant, submission state, clean scan and consent. Revoking either grant, withdrawing the submission, or deleting the member/evidence denies later reads. A replacement workspace assignment does not reactivate a grant bound to the revoked assignment. The owner can still read their own clean object; editors, other members and unassigned reviewers cannot. The capability remains short-lived and is bound to the object and current authorization.

This is authorization for invented local files, not a qualified reviewer workflow. There is no reviewer identity verification, member-facing grant approval, version lineage, criterion feedback, appeal, funded time or live service. The synthetic staff provisioning API has no public HTTP route. Those requirements remain on [CTP-010 #38](https://github.com/deepnative/deep-native-engine/issues/38), with full-MVP browser acceptance on [QA-002 #94](https://github.com/deepnative/deep-native-engine/issues/94).

Migration 022 is additive and rerunnable. Before real data, rollback is an application/schema revert after stopping the local preview. Once grant rows exist, disable the reviewer download path and preserve the rows until a reviewed retention/deletion plan exists; do not drop populated private authorization records as a routine rollback. The normal member deletion cascade removes the object's submission and its exact grants. This local behavior does not settle production retention or backup policy.
