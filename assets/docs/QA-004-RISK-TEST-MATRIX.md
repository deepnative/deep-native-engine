# QA-004: risk-based abuse and regression matrix

This is the executable-design handoff for [QA-004 #18](https://github.com/deepnative/deep-native-engine/issues/18) and [CTP-023 #42](https://github.com/deepnative/deep-native-engine/issues/42). Read it with the [threat model](QA-004-THREAT-MODEL.md), the [approved scenario register](../../tests/e2e/scenarios.json) and the [quality gates](context/QUALITY-GATES.md). **Existing** means a named synthetic local test already exercises the stated slice; **proposed** means the responsible feature issue must add and demonstrate it before its release gate. A proposed case is never counted in the current local-slice numerator. All 27 full-MVP requirements remain outstanding.

For each new capability, its owner must attach an acceptance criterion, the relevant risk IDs, a first-failure reproduction, deterministic unit tests for decisions, real PostgreSQL integration for state/races, and a browser journey for observable authorization or recovery. External providers may be simulated only at their explicit adapter boundary. Use isolated members and databases, controlled clocks and barriers or observed `pg_blocking_pids` for races. A sleep, a mock of the application policy, or a successful retry alone does not prove the invariant. The new scenario ID enters the approved release denominator before claiming coverage; the full-MVP register stays visible until its criteria are decomposed and passed.

## Execution and acceptance order

1. A feature owner copies the relevant M cases into that issue's observable acceptance and test design **before coding**. Record who owns any provider, staff, rights, privacy or payment decision; an unresolved launch prerequisite stays explicit.
2. Reproduce a defect with a real boundary and synthetic data before fixing it. For a race, show actual competing transactions or leases; for a provider error, distinguish no effect, confirmed effect and ambiguous effect. Keep denial responses and logs free of private content.
3. Run focused tests and the full `make verify` gate on the intended revision before every push. Record raw unit counts, approved scenario IDs and denominator, first-attempt pass/failure, PostgreSQL evidence and provider state. CI and independent review inspect the exact diff and reports.
4. CTP-023 reconciles every mapped risk, feature defect and outstanding scenario against the full release denominator. P0/P1 findings block the affected release until fixed and reverified; a local-slice pass never substitutes for live provider, restore, qualified reviewer or commercial evidence.

This matrix defines tests; it does not authorize executing a future issue, create a new staff role, select a provider, or certify the application.
