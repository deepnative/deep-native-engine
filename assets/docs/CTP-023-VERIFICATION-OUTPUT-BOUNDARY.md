# CTP-023: verification console output boundary

24 September 2026. [Issue #168](https://github.com/deepnative/deep-native-engine/issues/168) covers a bounded synthetic QA-004 M18 slice after [#137](https://github.com/deepnative/deep-native-engine/issues/137) and [#139](https://github.com/deepnative/deep-native-engine/issues/139). The accountable owner is @tomqwu. This is verification-tool privacy work, not hosted-runtime or qualified security approval.

## Observed failure and repaired behavior

Before the repair, the application runner inherited each `npm`/Node child's stdout and stderr, the Python launcher inherited the application's output, and `unittest.TextTestRunner` printed test names, assertions, captured text and failure traces. Synthetic private markers in either a successful or failing child/test reached the console even though the summary reports used safe stage diagnostics. New tests reproduced these leaks on the old code before the runner change.

The application runner now pipes and discards child output with a 1 MiB per-stream cap; a nonzero exit or output-buffer failure still fails at the code-owned command stage. It prints only fixed step names and records command exit status, never child text. The repository launcher sends the application runner's output to the null device; it reads and verifies the existing machine report for exact revision, successful status, unit thresholds and journeys. Repository-test discovery and execution run with Python streams and inherited native file descriptors redirected to the null device, then the console receives only aggregate run/failure/skip counts. File descriptors are restored even if discovery or a test raises. Test failure details remain in the in-process result for failure counting, not in a displayed or persisted trace.

This diagnostic tradeoff is intentional: a failing CI run gives a stage, command/status or aggregate test counts and a failed runner-owned summary report without publishing raw fixture values through the console. Reproduce a failure locally with synthetic inputs and focused tests to inspect details. The artifact scanner still gates display/upload, and missing, skipped, expected-failure, nonzero and stale-revision results remain failures. Raw test JSON, browser traces and other child-created artifacts can contain fixture text; the existing scanner recognizes only selected high-confidence credential patterns, not arbitrary private text. Those artifact contents, the standalone full-release runner and local developer commands have separate output boundaries. This change does not claim that every command or artifact an operator can display is safe to publish.

## Acceptance and limits

[Runner tests](../../tests/unit/verify-app.test.mjs) inject stdout/stderr markers into successful and failing synthetic child commands. [Repository tests](../../tests/repository/test_repo.py) inject markers into passing/failing Python test prints/assertions, a real nested native child and a disposable fake `npm` launcher. They assert no marker reaches console/report while failure status and aggregate counts remain intact. Exact-commit `make verify`, pre-push, PR/main CI and cleanup evidence are recorded on #168.

No application source, database schema, approved journey denominator or coverage exclusion changes. A scoped revert followed by the complete gate is the rollback. QA-004 M18 still requires hosted runtime logs, provider payloads, analytics, prompts, backups and compressed artifact review before live data/providers or release. Parent [#42](https://github.com/deepnative/deep-native-engine/issues/42) stays open; full-MVP browser coverage remains 0/100.
