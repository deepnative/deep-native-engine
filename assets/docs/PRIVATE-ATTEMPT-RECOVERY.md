# Private assignment attempts and recovery

A member can start a selected eligible sample assignment, save a private draft, submit its saved version locally, keep a private self-reflection, withdraw that reflection, revise and delete the attempt. Earlier submission text stays immutable while a revision is drafted. Attempts remain pinned to their original assignment version and goal; changing direction does not rewrite old work. Local submissions and portfolio statements are simulated, self-authored and unreviewed.

## Check an uncertain result

An assignment action may have completed even when its reply cannot be confirmed. The recovery page returns 503 and contains no stored private text or mutation form. Attempted text from the current POST remains available in a clearly labelled, read-only copy aid; it is not a saved receipt. Save, submission, revision and reflection pages retain their existing outcome-unknown titles and exact-attempt read links. Reads, starts and removals use **Assignment attempt unconfirmed** with **Check current private attempts**. Nothing is retried automatically. Open the current attempts using a valid authorized session, inspect the retained draft, submission or reflection, then decide whether another action is needed. Reloading is a read and does not create another revision or submission.

The same recovery response protects delayed attempt lists, detail, comparison and portfolio downloads. An uncertain portfolio read supplies no attachment. A definite pre-commit authorization denial remains distinct from an unavailable or possibly committed operation; an ordinary stale revision remains a conflict. Normal successful writes retain their redirects.

A recovery link does not renew an expired session, grant another member access or move old work into a new preview. If the current session has ended, its private data remains unavailable. The verification fixtures explicitly restore their invented principal's expiry only to inspect the committed outcome; that fixture control is not a product session-renewal feature. Existing session expiry is not a new retention or deletion policy.

## Lifetime and concurrency boundaries

Every attempt store operation uses the existing bounded transaction engine: up to three seconds acquiring a connection, five seconds for an individual command, and ten seconds for the total operation. Database-observed remaining authority can shorten those budgets. Authorization is checked before private work and before COMMIT, and is bounded through the reply and native connection handback.

Principal and workspace fences precede attempt and reflection locks. Session revocation, workspace deletion, exports, exact reflection withdrawal and attempt deletion retain their existing winner ordering. Expired or unknown connections are disposed. No rollback is queued behind an unresolved command or issued COMMIT, and no mutation is replayed. An uncertain COMMIT may be durable; disposal is not proof that it failed.

No table, historical row format, provider, retention schedule, entitlement or public renewal endpoint changes. Existing assignment eligibility, optimistic revision checks, submission limits and immutable snapshots continue to apply.

Earlier scenario IDs and the full-MVP requirements remain intact.
