# Local deletion recovery (#40)

This slice completes **previously accepted** local-preview account deletions after a process interruption or expiry of the initiating session. It does not create a new deletion request without a current member session and confirmation. The `/delete` route takes a shared principal lock and validates the member before marking the owned workspace, then checks database wall-clock expiry again before the marker commits. That lock blocks revocation/expiry updates but remains compatible with the foreign-key key-share lock of an in-flight workspace-first evidence upload, avoiding a lock cycle. A denied or expired request leaves no deletion marker. Once accepted, cleanup continues even if that session later expires or is revoked.

The persisted `workspaces.deleting_at` marker is the recovery queue. The runtime scans at startup and every five seconds in batches of ten, considering markers at least two seconds old so normal synchronous cleanup can finish first. The cursor advances past examined workspaces, including failed or locked ones, and wraps at the end; one failing request cannot indefinitely hide later requests. A pass never overlaps itself. Shutdown stops the timer and waits for its active pass before closing the database pool. Failures are logged only as generic retry notices without member identifiers, storage keys, paths or private content.

For each candidate, recovery locks the member principal and then its still-marked workspace. It removes all configured source and derivative object keys before deleting the principal and its existing owned-row cascade in one database transaction. A storage or database failure rolls the transaction back, leaving marker and metadata for another pass. The local filesystem removal is idempotent if a prior attempt already removed a key. A lost commit acknowledgement discards the connection and checks the principal on a new connection; it reports completion only when the row is absent. Competing workers skip a locked principal or workspace, and an unmarked workspace is ineligible. The initiating `/delete` request still returns a generic unconfirmed page on failure, never a false deletion receipt.

The existing [local deletion inventory](CTP-023-LOCAL-DELETION-INVENTORY.md) defines the configured record and object scope. This recovery does not erase PostgreSQL WAL/physical pages, backups, hosted replicas, provider copies, separately retained billing/legal records or historical unowned jobs. It does not assert complete export/deletion-job, legal retention, publication, moderation or full-MVP acceptance. Those remain open on #40, #12, #95 and #97 as applicable.

Fail-first real-PostgreSQL evidence showed that after partial source/derivative cleanup and session expiry, restart left the member principal behind. A separate fail-first upload/deletion lock probe observed a 503 response from the conflicting exclusive principal lock; the compatible shared lock repairs that ordering. The regressions now exercise the actual route failure, marker, expired session, restarted runtime and completed object/row cascade; another member survives. Further real-PostgreSQL checks cover two workers racing on the same marker and a new request expiring during its principal-lock wait. Unit tests cover bounded scanning, skip-locked/no-marker behavior, object and database failures, fairness, uncertain commit reconciliation and shutdown single-flight. Browser journey L95 verifies that a persisted accepted marker clears saved work and invalidates the old cookie in desktop and mobile Chromium. Exact commit, raw counts and CI are recorded on the delivery PR and issue.

Rollback: stop the preview before reverting. A pending marker must not be cleared to make the account appear active after any object bytes were removed. If recovery code cannot run, keep the marker and metadata, deny private access, and apply a reviewed forward repair or resume the compatible worker. Do not revert to an application that treats a failed synchronous deletion as complete.
