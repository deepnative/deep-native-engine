# CTP-009 local assignment attempts

This slice lets a member start one private text attempt for an already selected, currently eligible **synthetic published assignment version**. The attempt references the immutable `content_versions` row and records the member's goal at start. Starting, saving a draft and submitting its saved revision are distinct states. Submission is a local record only: no reviewer receives it, no evidence is uploaded, no competence is certified, and no entitlement is consumed. A profile background or optional paid plan never supplies authorization.

Migration `015-assignment-attempts.sql` creates a member-owned table with a unique member/content/version key and a composite foreign key to the pinned content. Browser session authorization and SQL token/ownership checks gate every operation. Writes also check the current choice, goal, background/tags, domain, experience, named local prerequisite, publication state and latest published version. A stale revision cannot overwrite a newer draft. Concurrent starts converge on one record; submission requires a saved response of at least 20 characters and explicit confirmation. Submitted text cannot be edited or resubmitted. Old goal/version/retired attempts remain readable to their owner but cannot be edited. Only the member can delete an attempt; deleting the preview account cascades the attempt rows. Session expiry denies access but is not itself a deletion.

The response is limited to 4,000 characters and the form requires confirmation that only invented/sample information is used. It stays in the local PostgreSQL preview, not object storage or any provider. The current 30-day session expiry does not establish a data-retention or automatic-purge policy. Any external evidence reference, reviewer access, durable retention schedule, or production deployment needs separate privacy/product decisions. Migration rollback is `DROP TABLE assignment_attempts` only after a deliberate data export/deletion decision; it destroys private drafts and is not an automatic deploy step.

Approved local scenarios L48–L50 cover general, non-IT professional and IT paths, private save/reload/submit/delete, stale tabs, goal and content-version changes, retirement, and unrelated-member denial. The full member-to-qualified-review journey remains outstanding. #103 owns structured prerequisite expansion, #93/#97 reviewed content, and #38 qualified review and evidence handoff. This local submission ID is not an evidence-store reference.

## Failed-write recovery

L51–L52 inject a deterministic PostgreSQL update failure for one synthetic attempt on desktop and mobile. A failed save or submission shows a no-store, copyable response page and an **unknown** outcome; it does not automatically retry or claim success. The member reloads the owned attempt to inspect the current saved revision or submission state before retrying. Optimistic revisions, the unique member/content/version key and the submitted-state guard still prevent stale overwrites and duplicate submissions. Validation, stale revisions, changed eligibility, expired sessions, same-origin form errors and transient storage errors have distinct messages. An expired session does not grant access to old database content; the response echoed from the member's own POST is only a local copy aid. A submit form carries a displayed response snapshot for that recovery purpose; it is never trusted as the submitted version or stored separately. Origin/CSRF checks continue to reject writes.

The recovery page uses read-only text with an accessible label and no automatic retry or submit control. Server responses set `Cache-Control: no-store`; the application does not log attempted response text or database error details. The PostgreSQL fault trigger exists only inside the disposable verification database and is removed after each scenario. Rollback of this follow-up restores the generic 503/redirect behavior without a schema migration; the database attempt constraints and privacy boundary from the preceding slice remain unchanged.
