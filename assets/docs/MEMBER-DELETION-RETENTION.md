# What stays when a member deletes their account

Deleting an account (My account → Delete your account) deletes the member's principal row. Everything else goes through `ON DELETE CASCADE` foreign keys that lead back to it: the learner profile, workspace, saved work, evidence and its derived records, sharing choices, export links, sign-in records and the rest. Stored files are removed before the row goes (`src/deletion-recovery.ts`), and a durable marker resumes a deletion that stopped part-way.

This page lists every table whose rows **don't** go with the account, and every member link in those rows. `tests/integration/member-erasure-coverage.test.ts` reads both tables below and compares them with the database catalog after all migrations:

- **ERASE-01/02:** a table that isn't removed through a cascade, or a column named `member_id`, `learner_id`, `owner_id`, `owner_principal_id`, `workspace_id` or `principal_id` without a cascading key, fails the test until it is listed here with a reason. An entry that no longer applies fails it too.
- **ERASE-03/04:** after a seeded member is deleted, a scan of every text, ID and JSON column finds their account ID, workspace ID, email fingerprint, display name and private note only in the rows marked "Kept" below.

The account page tells members the same thing in plain words before they delete (ERASE-06, browser scenario L318).

## Not covered here

- Hosted object storage, provider copies and database backups. Backups go only when they expire, on the hosting provider's schedule. Retention periods and backup expiry are open on #12 (D07/D08).
- A deleted member's ID inside another member's own records, such as a reply to their post. Those follow each feature's own rules.
- Staff accounts (`principals.kind='staff'`) are a separate kind and aren't deleted through this path.

## Member links in kept rows

| Column                                             | What happens on deletion                                                                        |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `account_role_events.learner_id`                   | Kept: the student reference stays so Change history can say a deleted account's coaches changed |
| `billing_change_events.member_id`                  | Kept: the student reference stays beside the amount for accounting                              |
| `browser_study_fixture_operations.workspace_id`    | Cleared by its trigger, with the actor, request, kind and instruction fingerprint               |
| `private_event_attendance_operations.workspace_id` | Cleared by its trigger, with the actor, registration, kind and instruction fingerprint          |
| `simple_invoices.owner_id`                         | Cleared; the invoice document keeps the billing recipient                                       |
| `workflow_review_operations.workspace_id`          | Cleared by its trigger, with the actor, kind, instruction and receipt                           |

Invoice retention is also checked in `tests/integration/simple-invoices.test.ts` (OFFPUR-05/07). The change history entries are described in [account types](ACCOUNT-TYPES.md) and on #734.
