# Local structured member export (#240, #345, scoped #40 continuation)

The local preview offers an active member a JSON download at `/api/member/export`. It is a synthetic local export, separate from the evidence source export. Each page is one transaction snapshot; a traversal across multiple pages is explicitly live. Each response uses a repeatable-read PostgreSQL transaction to check the current member session and read only that member ID. With v10, one response may be one explicitly bounded live page. It does not accept a member ID from the request. The response is `no-store` and a download attachment.

The [#330 authorization race repair](https://github.com/deepnative/deep-native-engine/issues/330) holds shared row locks on the member principal and owned workspace through assembly and commit. Revocation and principal deletion conflict with the principal lock; local account deletion first locks and marks the workspace, commits that phase, then removes objects and the principal. A workspace already marked for deletion is denied. These authorization locks alone leave ordinary record updates free to commit while a page retains its original repeatable snapshot; v10 additionally locks private text rows as described below. The transaction cannot be declared `READ ONLY` because PostgreSQL row locking requires a read-write transaction; export does not mutate member records.

Commit is the linearization point for revocation and deletion. If export acquires authorization first, a competing revoke/delete cannot complete its conflicting database change until export commits or rolls back. If revoke/delete wins, export returns denial or a generic unavailable result from the repeatable-read serialization failure; it never returns its stale snapshot. A database-clock expiry check immediately before commit withholds a snapshot whose session expired during assembly; it does not establish validity at the exact commit timestamp. This does not promise that revocation can recall an export already committed, or order HTTP receipt after database commit. A transaction-local five-second lock timeout matches the existing runtime's five-second statement timeout and bounds lock waiting for callers using other pools. Timeout, query/commit failure, denial and both size limits release the transaction; if rollback itself fails, the connection is discarded so it cannot return to the pool holding authorization locks. Unavailable responses expose no partial records or database details.

`local-member-records-v2` added immutable local assignment submission snapshots and sequence counts to the v1 sections: profile, exercises, lesson activity, assignment choice and attempts, milestones, opt-in career preferences and plans/drafts, retained private proposals, private practice, and local circle memberships. `local-member-records-v3` added only explicitly member-owned deterministic demo/test adapter-job metadata: ID, adapter, mode, status, attempt count, safe error and timestamps. `local-member-records-v6` added retained local AI permission receipts: opaque receipt and source IDs, exact revision, fixed local purpose and statement version, grant time and nullable withdrawal time. An owned local job exposes its receipt ID only when that receipt belongs to the same member; generic jobs have no local permission link. A withdrawn receipt is historical evidence, not current eligibility. The export omits source digests and bytes, idempotency keys, request content/fingerprints, operation text, provider references, raw provider errors, credentials and storage paths. Legacy/system jobs are not assigned to a member by inference. Snapshots remain owner-bound through their attempt and disappear with source or account deletion. Sections use stable ordering; timestamps are serialized as UTC by JSON. Withdrawn/rejected proposal text is null because the source rows are redacted. Deleted rows are absent. The original v1–v9 export failed with HTTP 413 when more than 100 current rows or 256 KiB would be returned; this intentional cap is superseded by the bounded v10 continuation below. Authorization denial is HTTP 403 and storage failure is HTTP 503 with generic errors.

The UI explicitly distinguishes this download from `/api/evidence/export`. Neither endpoint supplies a complete portability response. Structured export excludes evidence objects/bytes, derivatives, audit records, synthetic entitlement/billing data, provider copies and backups. Evidence export separately excludes most structured records. Live privacy, retention, backup expiry and hosted download/job authorization remain unresolved under #40 and PLAN-002. This implementation does not authorize a live community or release.

## v10 bounded live continuation: scoped #40 outcome

The member opens `/member/export`, then chooses **Download page N**. The browser fetches `/api/member/export?cursor=…`, saves those exact UTF-8 response bytes, and derives the next link only from that downloaded response. The HTML preview never supplies a continuation or claims completion. This prevents a record arriving between preview and download from displacing an undownloaded row behind a stale Next link. Every preview and download rechecks current owner authorization. Both routes use `no-store` and `Referrer-Policy: no-referrer`; the script is served from the same origin under the existing CSP and releases its temporary Blob URL. Failed authorization or reads remove the Next link and offer a safe restart without exposing the response body.

`local-member-records-v10` retains the prior field allowlists and adds `page.number`, `page.recordCount`, `page.consistency: "live-pages"`, `page.complete` and nullable `page.nextCursor`. Each response remains at most 100 section records and 256 KiB **including the complete serialized envelope, UTF-8 escaping, profile and cursor**. All named record arrays are present; arrays preceding the cursor are empty. Only an emitted record advances the cursor: a lookahead row or a byte-rejected row remains available on the next page. A profile or individual record that cannot fit returns an explicit 413 with no partial page. Normal application field limits are below that individual-record bound.

Sections have a fixed order. Within each section, v10 orders by its immutable primary-key JSON array using the exact same PostgreSQL expression for the keyset predicate and ordering. This deliberately replaces creation-date presentation order for ID-keyed sections. Composite versions are numeric; there is no timestamp serialization/precision dependency and no offset-based deletion skip. Assignment choice and career preference each have one row per member under their member-ID primary key. For unchanged records, traversing until `complete: true` retrieves every in-scope record exactly once. Completion means the end of this **live traversal**, not complete portability or a frozen multi-request snapshot. An insert behind an already passed key or a change to a previously downloaded record requires restarting; members are told to restart when records change and keep every downloaded file. Previously delivered copies cannot be recalled.

Continuation is an HMAC-SHA-256 authenticated, bounded, versioned token over section/key, next page number and a fixed 15-minute expiry, bound to the current session hash through the MAC input. The cursor body contains only record identifiers and pagination metadata, never private text, credentials or the session hash. A process-local random signing key avoids a new retained export store; restarting the server invalidates outstanding cursors. Wrong session/owner, malformed/forged/obsolete/oversized/expired cursors are denied; expired or restarted traversal must begin again. This adds no provider, schema, saved snapshot, hosted job, or retention promise.

Authorization principal/workspace locks remain held through each page commit, with session expiry checked again immediately before commit. Every private text section (exercises, attempts, milestones, career entries/drafts, proposals, workflow feedback and practice) takes bounded shared row locks. A deletion, withdrawal or correction that changes a snapshot tuple before its lock is acquired fails closed; a text page locking first may finish before the competing change commits. Ordinary metadata-only sections retain repeatable-read behavior. Resumed submission pages independently **await a bounded attempt-parent lock query in UUID order before reading immutable child submissions**. The child query is restricted to those locked parent IDs; no child-first joined row lock can invert series deletion's parent-before-child order. Both transaction-local statement and lock timeouts are five seconds, including callers with a separately configured pool.

Verification adds fail-first real-PG >100-row and >256-KiB tests, full distinct traversal, mixed-case/mixed-length/composite keys, session/process binding, cursor tampering/expiry, earlier-key deletion without skipping, resumed redaction, text deletion in both orders and parent-before-child submission deletion in both orders. L90 extends the preserved register to `initial-learning-v60` (90 approved IDs): desktop/mobile browsers download all 121 records across bounded files, including an insertion between preview and actual download, and deny cross-member, forged and revoked continuation. Existing L61/L67 and provisional F-BUILD-08-A retain their assertions with the v10 filename/UI contract. Full-MVP accepted coverage remains 0/100.

Rollback introduces no migration. A return to v9 loses functional continuation and must also restore compatible UI/script handling; outstanding v10 cursors should fail and members must restart. Never remove redacted source markers, authorization locks or parent locks to restore the old cap. Parent #40 remains open for its hosted retention/backup, broader portability, participation/publication and qualified privacy decisions. This is local synthetic functionality only.

## v11 private assignment reflections: scoped #390 outcome

`local-member-records-v11` adds `assignmentReflections` after immutable `assignmentSubmissions`. Each retained row names the exact attempt and submission sequence, original content ID/version, the member's three bounded self-reflection fields, optimistic revision and the fixed `SELF-REPORTED · SIMULATED · UNREVIEWED` label. These notes are member-authored local learning records, not expert assessments or credentials. A deleted reflection is a text-free tombstone and is omitted; deleting its attempt or account cascades through the row. A later save cannot resurrect deleted text. The owner export locks the same principal, workspace and attempt rows used by reflection writes and attempt deletion, preserving deletion/withdrawal ordering for a page. Continuation remains bounded and live; old v10 cursors are invalid, and members restart export after the version change.

Rollback must disable the reflection write and export routes together until the v11 projection or an equivalent safe replacement is restored. Preserve the additive table and its tombstones during a binary rollback; do not expose the reflection to reviewer/staff or claim hosted backup erasure. Parent #38 still requires separately authorized qualified review, consent, funded time and appeal terms.

The [#431 private proposal revision flow](PRIVATE-PROPOSAL-REVISIONS.md) advances the structured payload to `local-member-records-v15`. Each owned proposal adds exact `rightsAttestedRevision`, `rightsAttestedAt` and nullable current `feedback` (`text`, `reviewedRevision`, `requestedAt`). Dates serialize as timestamps; the nested feedback timestamp is already a PostgreSQL JSON string. Legacy exact rights revision remains unknown/null; no confirmation is fabricated from historical timestamps. Feedback follows the proposal's locked current row through returned edits/resubmission, and is replaced by a later request. Withdrawal/rejection removes it with proposal text; account deletion cascades the source and audit. Export includes no moderator identity or audit. Cursor v2, stable section positions and the 100-record/256-KiB limits remain unchanged. A page locked first may complete before withdrawal; withdrawal committed ahead of a waiting repeatable snapshot causes fail-closed recovery, and a fresh page reflects redaction. An older binary hides these disclosed fields and cannot safely handle the new state or revised rights; disable affected proposal/export routes during rollback until an equivalent compatible implementation is restored.
