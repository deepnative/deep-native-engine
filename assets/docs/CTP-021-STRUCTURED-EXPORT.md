# Local structured member export (#240, #345)

The local preview offers an active member a JSON download at `/api/member/export`. It is a synthetic, current-state snapshot, separate from the evidence source export. A single repeatable-read PostgreSQL transaction checks the current member session and reads every section for that member ID. It does not accept a member ID from the request. The response is `no-store` and a download attachment.

The [#330 authorization race repair](https://github.com/deepnative/deep-native-engine/issues/330) holds shared row locks on the member principal and owned workspace through assembly and commit. Revocation and principal deletion conflict with the principal lock; local account deletion first locks and marks the workspace, commits that phase, then removes objects and the principal. A workspace already marked for deletion is denied. These authorization locks leave ordinary record updates free to commit while the export retains its original repeatable snapshot. The transaction cannot be declared `READ ONLY` because PostgreSQL row locking requires a read-write transaction; export does not mutate member records.

Commit is the linearization point for revocation and deletion. If export acquires authorization first, a competing revoke/delete cannot complete its conflicting database change until export commits or rolls back. If revoke/delete wins, export returns denial or a generic unavailable result from the repeatable-read serialization failure; it never returns its stale snapshot. A database-clock expiry check immediately before commit withholds a snapshot whose session expired during assembly; it does not establish validity at the exact commit timestamp. This does not promise that revocation can recall an export already committed, or order HTTP receipt after database commit. A transaction-local five-second lock timeout matches the existing runtime's five-second statement timeout and bounds lock waiting for callers using other pools. Timeout, query/commit failure, denial and both size limits release the transaction; if rollback itself fails, the connection is discarded so it cannot return to the pool holding authorization locks. Unavailable responses expose no partial records or database details.

`local-member-records-v2` added immutable local assignment submission snapshots and sequence counts to the v1 sections: profile, exercises, lesson activity, assignment choice and attempts, milestones, opt-in career preferences and plans/drafts, retained private proposals, private practice, and local circle memberships. `local-member-records-v3` added only explicitly member-owned deterministic demo/test adapter-job metadata: ID, adapter, mode, status, attempt count, safe error and timestamps. `local-member-records-v6` added retained local AI permission receipts: opaque receipt and source IDs, exact revision, fixed local purpose and statement version, grant time and nullable withdrawal time. An owned local job exposes its receipt ID only when that receipt belongs to the same member; generic jobs have no local permission link. A withdrawn receipt is historical evidence, not current eligibility. The export omits source digests and bytes, idempotency keys, request content/fingerprints, operation text, provider references, raw provider errors, credentials and storage paths. Legacy/system jobs are not assigned to a member by inference. Snapshots remain owner-bound through their attempt and disappear with source or account deletion. Sections use stable ordering; timestamps are serialized as UTC by JSON. Withdrawn/rejected proposal text is null because the source rows are redacted. Deleted rows are absent. The export fails with HTTP 413 when more than 100 current rows or 256 KiB would be returned; it never returns a truncated response. Authorization denial is HTTP 403 and storage failure is HTTP 503 with generic errors.

The UI explicitly distinguishes this download from `/api/evidence/export`. Neither endpoint supplies a complete portability response. Structured export excludes evidence objects/bytes, derivatives, audit records, synthetic entitlement/billing data, provider copies and backups. Evidence export separately excludes most structured records. Live privacy, retention, backup expiry and hosted download/job authorization remain unresolved under #40 and PLAN-002. This implementation does not authorize a live community or release.

Verification: the controlled real-PostgreSQL fail-first tests reproduced both revocation and local deletion completing while the export transaction remained in progress, followed by private records being returned. A separate fail-first test reproduced a session expiring during assembly while private records were still returned. Review also identified failed rollback cleanup; its fail-first reproduction left the live transaction's locks in the pool and caused another connection's update-lock request to time out. The regressions now observe actual database blockers and transaction status to assert both lock orderings, expiry denial, unrelated-member independence, bounded lock timeout, failure/cap recovery, and successful update-lock acquisition after rollback failure discards the client. They also preserve active/expired/revoked isolation, current/deleted/redacted rows, both limits and the repeatable snapshot across ordinary updates. L61 exercises the owner link, cross-member result, revoked/deleting/expired denials and restored synthetic access in desktop/mobile browsers; L67 covers attributable deterministic job metadata and deletion. No new browser scenario or coverage denominator is introduced. The repository gate reports exact revision and raw counts in `artifacts/application-verification.json`; attach the first-attempt local, PR and main CI results at handoff.

Rollback of the original export route/UI and `memberExportStore` wiring does not remove member records. The v2 snapshot section introduced by #300 and v3 member-job metadata introduced by #302 have their own schema and retention boundaries; preserve their rows and published export contracts until a separately reviewed migration/export plan accounts for them.

The #330 repair introduces no migration or new exported field. Its operational cost is that a same-member revoke/delete can wait for the bounded export transaction; unrelated members remain independent. Reverting only the locking/expiry repair restores the reproduced disclosure race. If rollback is necessary, disable the structured export route/store until a safe replacement is verified; leave member records and existing export contracts intact. Hosted exports, backup reconciliation and full-MVP retention/deletion acceptance remain outside this local repair.

The #345 v6 projection introduces no new retention table: it exposes a bounded allowlist from already retained local permission receipts and their owned jobs. Returning an older export binary would hide that retained history from the download without deleting it. If v6 is relied on as a member-facing export promise, keep the route disabled during such a rollback until an equivalent safe projection is restored. Source/account deletion continues to cascade the rows; no live backup expiry or legal retention claim follows from the local export.

The [#351 private draft-correction slice](CTP-013-PRIVATE-PROPOSAL-CORRECTION.md) advances the structured export to `local-member-records-v7` and adds the proposal's current positive `revision`. The proposal section still contains only the current retained row per proposal; correction does not create exported copies of earlier text. Withdrawn and rejected rows retain null private text, while account deletion removes the row. The same owner authorization, repeatable snapshot and size limits apply. A rollback to a v6 binary hides the new revision field and, more seriously, its older proposal submission path does not require an expected revision. Keep both edit and submit routes disabled until the revision-guarded binary is restored; preserve the additive schema and private rows. This does not resolve hosted retention or a complete portability contract.

The [#353 one-note practice withdrawal](CTP-015-PRIVATE-PRACTICE.md) advances the owner snapshot to `local-member-records-v8`. Each retained private-practice row explicitly distinguishes a saved response from a withdrawn marker. A withdrawn row has `response: null` and its withdrawal time; no prior note text or simulated comparison is exported. The existing single-snapshot authorization, ordering and record/byte caps remain. Account deletion removes the marker. Reverting to a v7 export binary would omit that disclosed state; disable the structured export until an equivalent marker-aware projection is restored. This local redaction does not settle hosted backup retention or full portability.
