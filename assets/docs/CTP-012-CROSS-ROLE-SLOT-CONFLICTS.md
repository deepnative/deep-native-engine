# CTP-012: cross-role sample-slot integrity

Issue [#335](https://github.com/deepnative/deep-native-engine/issues/335) corrects overlapping commitments in the local synthetic availability and hold slices. A staff principal occupies a non-retired sample slot in both the primary and backup roles. Neither principal can occupy another overlapping slot, including reciprocal A/B rosters, shared backups, or different domains/services. UTC windows are half-open: an hour ending at 16:00 does not conflict with an hour starting at 16:00. Retiring a slot removes its conflict contribution and retains its row, version counter, holds, reservations and immutable ledger events.

## Correction and lock order

Migration 037 adds one read-only SQL predicate, `sample_slot_conflicts`, shared by slot creation, eligible preview and new synthetic holds. It compares both principal IDs against both roles of every overlapping non-retired slot. The current slot is excluded when checking preview/hold eligibility. All retained conflicting rows are hidden and refused, rather than choosing a winner after the fact. Verification, current staff identity, coverage dates, capacity, category/ownership and operator checks remain in their existing paths.

Creation retains its transaction-scoped advisory locks for the deduplicated primary/backup principal IDs in sorted order. All creates acquire that order before the roster row lock and before reading conflicting slots. A competing transaction then reads the committed winner after its advisory-lock wait; reversing primary/backup does not reverse the order. The controlled race test starts two separate connections behind an advisory-lock barrier, observes both blocked in PostgreSQL through `pg_blocking_pids`, releases the barrier, and requires exactly one persisted winner for every role pairing. A four-second statement timeout and bounded observation loop fail a stalled race; retries do not provide acceptance evidence.

New holds apply the same conflict predicate before changing grants, reservations, holds or ledger events. Existing hold idempotency and explicit expiry remain unchanged: a replay returns the existing hold, and expiry can release its reservation even while retained slots conflict. Retiring a conflicting slot restores preview eligibility only when the other existing eligibility checks pass. No migration deletes, retires or silently repairs existing slot/hold/credit history.

## Acceptance and limits

The dedicated real-PostgreSQL suite covers sequential and simultaneous primary/primary, primary/backup, backup/primary, backup/backup and reciprocal conflicts; cross-domain overlap; full persisted-state equality after denied creates and holds; adjacency; retained conflict exclusion; member/coach and revoked-operator denial; verified-roster requirements; migration replay; immutable event preservation; and existing hold expiry/replay. Existing availability and hold suites retain capacity, timezone-independent UTC, last-credit concurrency, owner/category denial and expired-member/grant recovery checks. Browser L64 extends its existing desktop/mobile journey with visible conflicting-window exclusion and recovery after retirement without adding booking controls or exposing staff evidence.

This is a synthetic local integrity boundary, not a live appointment, qualified roster, commercial entitlement or approved cancellation/rescheduling policy. Direct database administrators can still insert historical fixture rows; preview/new-hold checks fail closed for them. There is no roster-editing API in this slice; new write paths that change roster principals or slot times require the same concurrency design. Parent [#29](https://github.com/deepnative/deep-native-engine/issues/29), [#42](https://github.com/deepnative/deep-native-engine/issues/42), real roster/capacity decisions #13/#96 and the full-MVP gate remain open.

For rollback, stop synthetic slot creation and new holds before reverting the caller/migration functions as one reviewed change. Preserve all slot, hold, reservation and event rows. Removing this predicate while continuing writes restores the reproduced defect; it is not a safe data repair. An operator may retire an unwanted sample slot through the existing authorized path without deleting its history.
