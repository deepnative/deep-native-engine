# Private assignment submission revisions (#300)

This local synthetic slice lets a member submit an assignment, reopen it as a new private draft, and submit again, up to ten submissions per attempt. Each submission keeps its own response, timestamp and sequence in `assignment_submission_snapshots`; the mutable attempt row holds the current draft and count. The first migration backfills previously submitted attempts as sequence 1 without changing their response. Subsequent submissions write the attempt update and snapshot in one PostgreSQL statement, so a failed snapshot insert rolls back the state change. Revision clears only the mutable draft; it never edits a snapshot.

The member can see the history and download it through the owner-scoped `local-member-records-v2` structured export. A revision requires the same active member session, current assignment version and direction eligibility as submission. A retired or changed assignment, changed goal, another member, or an exhausted count cannot start a revision. The account's existing delete action removes the attempt and its snapshots together. This slice adds no staff review, scoring, appeal, automatic matching, live service, or retention policy.

Verification: the real-PostgreSQL tests cover backfill, immutability, owner isolation, concurrent revision, eligibility changes, the ten-submission cap, atomic failure and delete cascade. Approved browser journey L66 covers the member flow, export, cross-member denial, retirement and deletion. The exact revision and aggregate gate results are recorded in `artifacts/application-verification.json` at delivery.

Rollback: disable the revision route and controls if needed, but preserve `assignment_submission_snapshots` and its owner-scoped export so existing submissions remain readable. Dropping the table or reverting the v2 export requires a separate reviewed data migration and retention decision.
