# Demonstrate completed milestones

Owner request, 2 October 2026: show a demo at each milestone completion. This procedure applies after completed product slices as well as milestones; a child's completion does not imply its parent is complete. Follow [the team delivery workflow](TEAM-WORKFLOW.md) and retain every verification, merge, main-CI and branch-cleanup gate.

## Show the usable result

Run the verified-main result in a dedicated local preview, or use a preview whose hosting is already authorized. Give the owner a direct access link and a short walkthrough of the main user journey: what changed, actions actually performed, observed outcomes and remaining limitations. Record the revision, date/timezone, environment and actual provider state in [the evidence template](../templates/EVIDENCE.md). Screenshots or a short recording help when they make the result easier to inspect; CI output or a feature list alone is insufficient.

Keep the preview available for the owner's inspection when practical. State that a localhost link works only on the machine running it, its lifetime, and how to restart it. Use [the local setup instructions](VERIFICATION.md) for ordinary previews. If the demonstrated state needs isolated seeded fixtures, document their safe setup and resource ownership without publishing credentials. A captured session is historical evidence; it does not prove that its old URL still runs. If access or reproduction is unavailable, record the exact blocker, responsible owner and bounded next action; do not invent a successful demonstration or hide the missing access. This is a handoff gap, not permission to hold an otherwise green PR for optional review or request already-granted merge approval again.

Use invented data and a dedicated preview database/storage/server, separate from any active quality-gate resources. Never expose credentials, session tokens or private member files in URLs, prose, screenshots or recordings. Stop/remove only resources owned by the preview after checking their identity; preserve verification resources and unrelated work. Do not infer live provider operation from a deterministic simulation, qualified review from automated checks, or full-MVP acceptance/deployment from a merged slice. Creating or publishing a hosted preview still requires the applicable deployment authorization.

Update the concise [product README](../../../README.md) when a completed slice changes what users can actually do. Describe delivered capabilities and their limits, not every planned issue. A documentation/tooling-only milestone demonstrates its changed artifact or procedure; do not fabricate an application feature or add a product-feature claim for a prose edit. Every handoff still recommends one bounded next action with live model/effort and its dependencies/claims.

## Worked example: #437, local requests using test units

[Accepted scope and actual demo record](https://github.com/deepnative/deep-native-engine/issues/437#issuecomment-5962905211); [merged PR #439](https://github.com/deepnative/deep-native-engine/pull/439). Demonstrated on 2 October 2026, 19:02–19:06 America/Toronto, verified main `4595c573017fb0ae7de13c8d0a1fc552c6867f5e`. Main CI passed before the demo. A dedicated isolated PostgreSQL database and temporary private storage served a loopback preview using the deterministic private-test adapter, separate from verification resources.

The browser walkthrough used an invented learner and two invented text samples with explicit rights and exact-source permission. A local fixture seeded two existing study-request units; this was not a purchase/grant API. The member held one request, ran it once and reloaded its consumed receipt. The member held the second request and withdrew permission before dispatch, observing release. The balance page then showed **1 usable, 0 held, 1 consumed**. The README's local-test-request feature describes that delivered behavior.

The demonstration's localhost origin was port 63439; it is an ephemeral local address, not a permanent or deployed product URL. Captures and the isolated launcher/fixture helpers were retained in the delivery environment and linked in the issue evidence; they are not portable repository assets. On that original machine only, after stopping the owned old preview, keeping its clean checkout at the demonstrated SHA and confirming the helper is present, restart with `DNE_DEMO_EXPECTED_SHA=4595c573017fb0ae7de13c8d0a1fc552c6867f5e node /private/tmp/dne437-demo-runtime.mjs`. Use its newly printed origin, onboard one invented learner, then run `node /private/tmp/dne437-demo-fixtures.mjs seed`; use its `clean` action only for invented samples in that dedicated preview. The new database starts empty and a new port is expected. These helpers deliberately refuse a different revision; do not bypass their check or delete unrelated resources to restart a demo. To reproduce from a new checkout, follow the local setup guide and [the request operation guide](../PRIVATE-LOCAL-AI-TEST-REQUESTS.md), configure an isolated invented-data test fixture with existing study units, and repeat the explicit hold/run/reload and never-started withdrawal flow. If those fixture resources are absent, record that access limitation before claiming reproduction. Never point a new demo at an active gate database.

This proves the observed private local journey, not live AI, a bought allowance, qualified review, full-MVP completion or production deployment. #188 and broader parents remain open for their other acceptance criteria. #438 demonstrates this procedure and instruction changes, with no new application capability claimed.
