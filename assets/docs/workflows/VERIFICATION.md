# Verification contract

## Reproduce the complete check

Prerequisites: Git, GNU Make, Python 3.11+ (CI uses 3.12), Node 24 at the version in `.nvmrc`, npm, and Docker with Compose and a running daemon. On macOS Docker Desktop or a running Colima VM works. Linux browser installation may request system-package privileges. Native Windows is not tested; use WSL with Docker.

```sh
make setup
make verify
make dev
```

Open `http://127.0.0.1:3000`. `make setup` installs the local hook, runs `npm ci`, starts the digest-pinned PostgreSQL 18 image on loopback port 54329, installs Chromium, Firefox and WebKit with their OS dependencies, and copies `.env.example` only if `.env` is absent. A pre-existing PostgreSQL 18 fixture on that loopback port also supports verification when Docker CLI is unavailable, provided matching PostgreSQL 18 `pg_dump` and `pg_restore` clients are on `PATH`. No provider credentials are needed. The published database password is a local disposable fixture. Never reuse it for hosting. Startup applies the idempotent migrations and listens on loopback only. `DNE_DATABASE_URL`, `DNE_PORT`, `DNE_APP_MODE` and optional per-adapter mode variables configure the preview; dotenv is read by the Node start commands. Demo mode requires the local development database; verification starts the compiled server in test mode against its random isolated database.

`make bootstrap` refuses a conflicting hook path or active foreign pre-push hook. Repeating it is safe. In worktrees the local Git config may be shared; the relative `.githooks` path resolves within each worktree. `make db` restarts the local database. `npm run build && npm start` runs compiled output. Stop the app with Ctrl-C; `docker compose stop` preserves data. For an intentional deletion of **all local preview data**, stop the app and run `docker compose down --volumes`; then `make db` creates an empty database. Do not use a reset to conceal a test failure.

## One gate locally, before push and in CI

`make verify` executes:

1. Repository scope, immutable 25-file archive, 55 planning IDs, dependencies, model routing, skill/agent definitions and local links; regression tests include missing application gates and stale/wrong revision evidence. A high-confidence byte scan of tracked and nonignored untracked files rejects GitHub/OpenAI/AWS credential shapes and private-key headers. Its failure names an opaque file reference, line and rule but suppresses the matched value and raw filename; disposable negative probes cover tracked and untracked source. A separate generated-artifact scan runs after application verification and again in CI before report display or upload, including after verification failures. It scans bounded ZIP trace members as well as plain artifacts and rejects malformed, encrypted, unsafe or unsupported compressed artifacts. CI retains safe failure traces and skips display/upload if artifacts are missing, unsafe or contain a matching marker. These bounded scans do not inspect ignored local files, arbitrary private text, earlier CI console output, runtime logs or provider systems, and do not replace release security review. See [the ZIP artifact boundary](../CTP-023-ZIP-ARTIFACT-SCAN.md).
2. Before any application command, an offline installed-dependency prerequisite compares the root manifest with the committed lock entries, checks every installed package against its exact locked name/version, and asks npm to validate the complete installed graph. Missing or stale required packages and invalid/extraneous graph edges fail with a fixed diagnostic; raw npm output is suppressed. Run `npm ci` to restore the locked installation, then rerun `make verify`. Platform-omitted optional packages remain optional. This check does not claim byte-for-byte integrity of files extracted into `node_modules/`.
3. Locked-tool formatting, ESLint and TypeScript checks.
4. Vitest behavioral unit tests and V8 coverage of **all `src/**/*.ts` and first-party `public/**/*.js`**, including unimported files, views, adapters, startup and browser scripts. Require >=99% statements, branches, functions and lines globally and per file, checked from raw counts. No executable application exclusions. SQL is declarative and exercised against PostgreSQL; CSS is checked and rendered in browser tests. Tests, tooling and generated `dist/` are outside the application coverage denominator and have separate behavioral checks.
5. Isolated negative probes proving that unimported TypeScript and public JavaScript, a deliberately broken CSRF comparison, and a broken end-of-month billing anniversary fail. The billing probe checks the named behavioral assertion in the machine-readable test report and stores the failed mutant report under `artifacts/probes/`; the production source is unchanged.
6. Production TypeScript build, PostgreSQL integration tests and the complete desktop/mobile Chromium browser matrix against the compiled server and real database. The runner creates separate random `dne_test_<32-hex>` databases for the approved local and provisional suites and drops only those databases in `finally`. Test helpers refuse other database names. Nothing truncates the development database.
7. Exact scenario mapping to [the approved local register](../../../tests/e2e/scenarios.json): >=99% approved slice journeys, 100% critical journeys and executed tests. All projects must pass for a journey to count. Missing/empty reports, skips, expected failures, focused tests, retries, duplicate/unmapped scenarios and reduced preserved full-MVP inventory fail. A separate [L53 local keyboard register](../../../tests/e2e/cross-browser-scenarios.json) requires one first-attempt execution on desktop and narrow viewports in each of Chromium, Firefox and WebKit against the same isolated test database. Narrow viewport does not claim a physical mobile device. This does not change approved local or full-MVP denominators, establish manual Safari/VoiceOver accessibility evidence, or close the release criteria in #109. The 27 outstanding full-MVP families now map to 100 proposed, separate browser IDs under `full-mvp-v1`; this local gate reports 0/100 and does not claim the whole MVP. The future full-release gate is documented in [QA-002 journey traceability](../QA-002-JOURNEY-TRACEABILITY.md).
8. A separate provisional full-MVP browser suite runs the currently mapped proposed cases on both registered Chromium projects against a second isolated test database. Its fail-closed result is recorded as unapproved evidence; it does not change the approved full-MVP 0/100 release count or make the full-release gate pass. Each provisional case must complete every current required action/assertion check in one first-attempt execution on each browser; the provisional and full-release evaluators use the same exact check-token validation, rejecting a missing, duplicated or stale token on either browser. A completion token is structural evidence, so the underlying assertions and traces still need review. The `npm run verify:full-e2e` command runs its own isolated browser suite and requires the separately reviewed mapping decision, a clean exact revision, a matching fresh run and retained traces; it does not accept a supplied JSON report. Each of the 100 full-release IDs must likewise complete all its registered required checks; the technically approved mapping has 206 checks. The mapping decision is recorded, but accepted full-MVP coverage remains 0/100, so a full-release pass is unavailable. See [QA-002 journey traceability](../QA-002-JOURNEY-TRACEABILITY.md) for the current provisional inventory and its review limits.
9. Runtime dependency audit (`npm audit --omit=dev --audit-level=high`). This requires network access; unavailable audit data fails the gate. It does not replace source/security review.
10. The separately scoped local learning prototypes: generated-reader consistency, module syntax, JSON and font-provenance checks, then the existing prototype (13), authoring (12), reader (124) and GUI (16) browser cases on an isolated loopback server. All 165 cases must pass once, with unique case names and no retries. Their report is `local-content-prototypes`; it does not add to application coverage or approved journey denominators. The repository permits only the explicitly listed local assets, so an extra executable file still fails scope validation.

Coverage includes data-only modules with measured executable initializers. Such a module may have zero functions or branches; it must still have positive, measured statement and line counts. Global denominators remain positive, and the 99% thresholds, exact source inventory, skipped-count rejection and raw-total reconciliation are unchanged.

The application verification runner uses fixed stage diagnostics for setup, evidence parsing and database failures; it never serializes the thrown value. Database deletion, connection shutdown and private-storage cleanup are attempted independently. Any cleanup failure, idle database error or unwritable final report fails the run. The Python repository runner likewise withholds unexpected exception details, captures Git error output, and replaces input-derived paths/metadata with stable opaque references; intended code-owned gate reasons remain actionable. A failed report write returns nonzero. See [the Python boundary evidence](../CTP-023-SAFE-REPOSITORY-DIAGNOSTICS.md). Runner-owned summaries and CI console output have the bounded M18 protection; ZIP trace artifacts now receive a bounded credential scan, while arbitrary private text and hosted/provider logs remain separate boundaries. See [the bounded M18 evidence](../CTP-023-SAFE-VERIFICATION-FAILURES.md) and [the ZIP artifact boundary](../CTP-023-ZIP-ARTIFACT-SCAN.md).

Each application child-command report also records fixed stdin/output modes, the capture limit, output byte counts, an allowlisted signal, a launcher/buffer failure category, and fixed Vitest/npm error-banner flags. These fields help investigate a passing test JSON report with a nonzero process exit without retaining child output, exception text or member data. A banner flag is a clue, not a root-cause finding. Preserve the first failed report; a later green run does not repair it. A passing Vitest JSON report never overrides a failed child-process exit.

Reports in ignored `artifacts/` include repository/application revision and tree, dirty state, runtime/environment, commands, raw unit counts, unit/integration assertions, browser mapping, failure traces and probe results. Each run replaces previous authoritative reports; repository status becomes verified only after fresh application evidence matches its revision. No report from a failed run constitutes a pass. CI uploads evidence for 14 days using synthetic fixtures only.

A dirty working-tree run is useful during editing but is not evidence for a later commit. Commit first, then rerun `make verify`. The pre-push hook requires a clean checkout and every non-deletion pushed ref to equal HEAD, runs the complete gate again and rejects changes made during verification. No `--no-verify`, threshold reductions, silent exclusions or retry-only passes.

### L102 native submission evidence

If the existing L102 starter-practice journey fails, its `native-submission-observation` JSON attachment records bounded native event types, allowlisted key/element shapes, observed focus and form-validity flags, submission events, and normalized request route classes/statuses. Schema v2 retains the newest bounded tail: at most 256 events and less than 64 KiB, evicting the oldest history when either limit is reached so late-action evidence remains available. The retention policy, eviction count, truncation, discarded input and known capture failures remain visible. It excludes form values, member text, cookies, CSRF/session values, arbitrary attributes and URLs. Capture reads validity state without invoking validation, changing focus, cancelling defaults or submitting; all original keyboard actions, three audiences, assertions, deadlines and journey denominators remain unchanged.

The attachment uses metadata already delivered to the runner and does not wait for a failed renderer. Its last observed state is not a fresh final-page read. Default-prevention flags are observation-time samples; the microtask phase does not guarantee final dispatch state. Binding messages may be lost across navigation and observation may affect timing, so missing events do not prove that no native event occurred. The original [#543 failure](https://github.com/deepnative/deep-native-engine/issues/543) remains unresolved until actual failing evidence supports a cause; a later passing run alone is not a historical repair. Preserve the original artifact and inspect native delivery, validation/default prevention and actual POST/response evidence before selecting a correction. Passing tests receive no extra attachment.

Contributors can still run the full gate locally on macOS. The hosted OS choice does not change the desktop/mobile Chromium approved browser matrix or its scenario coverage; Linux WebKit is not manual Safari evidence. Force pushes and branch deletion are disabled. No separate approval count is imposed by this setting; the owner's standing CI-based merge authorization and any applicable review requirements still govern. Read back the active setting with `gh api repos/deepnative/deep-native-engine/branches/main/protection`; an unavailable or changed required check must be investigated before merging, rather than bypassed. This repository setting is outside Git and cannot be reproduced from a checkout alone.

## Review and merge evidence

Follow [the team workflow](TEAM-WORKFLOW.md). The author records a self-review of the actual diff and reports; a separate reviewer inspects them when requested or required. Before merging, verify current head/base, actual required reviews and successful current CI; guard the merge with expected head SHA. Do not hold a green PR solely for optional review. Then verify the `main` workflow for the resulting merge commit and safely fast-forward local main. A green PR does not prove post-merge main, deployment or commercial readiness.

## Recovery

Fix failures, then regenerate evidence on the changed revision. Preserve archive hashes; never regenerate the manifest to hide corruption. Extend scope validation and coverage together when adding an executable source type. Resolve hook conflicts deliberately. If the database is unavailable, start it with `make db`; do not skip integration/E2E. Failed test-database cleanup is a gate failure and records the problem. Refresh stale browser forms after restarting the app. See the [slice decision record](../INITIAL-LEARNING-SLICE.md) for privacy, retention, migration and release limitations.

## Synthetic restore rehearsal

The integration gate also runs [the isolated restore rehearsal](../CTP-025-SYNTHETIC-RESTORE.md) using PostgreSQL tools inside the existing Compose fixture or the explicitly attested dedicated fixture below. It creates fresh source/target databases, restores a synthetic archive plus private object copy, verifies corruption rejection and restored privacy/deletion behavior, and removes its owned resources. `artifacts/restore-drill.json` records exact revision/tree, fixture counts and measured local durations after successful cleanup. It is local synthetic evidence, not approved production RPO/RTO or a production backup/retention policy. Arbitrary database overrides do not satisfy this rehearsal.

### Optional dedicated verification instance

When the shared local PostgreSQL instance has accumulated state or is serving other workers' previews, use a separately owned instance for the **complete unchanged gate**. Keep full browser verification serialized: a separate database server does not isolate port4317. Do not reset, stop, tune or delete the shared Compose server/volume. This option changes neither native cleanup deadlines nor coverage/test requirements; it reduces server-state interference without guaranteeing a10s native DROP or proving the cause of an earlier failure.

Before creation, publish the claim and record an unused loopback port, a unique container name and a newly generated volume identity. The example uses64329; verify it is free and adapt the port if necessary. The image must match the digest in `compose.yaml`. Use a durable local volume and default PostgreSQL durability/checkpoint settings, never tmpfs or disabled fsync. Preserve the successful creation result, exact full container ID, volume identity, claim, image, endpoint and timestamp in a private ownership record outside the repo. Labels support consistency checks; they do not establish freshness or authorize deletion by prefix.

```sh
set -eu
# Replace this example with your published unique claim before creation.
export DNE_TEST_POSTGRES_CLAIM='DNE-2026-10-14-513-your-worker-unique-claim'
dne_verify_nonce=$(node -e 'process.stdout.write(require("node:crypto").randomBytes(16).toString("hex"))')
export DNE_TEST_POSTGRES_VOLUME="dne-verify-$dne_verify_nonce"
dne_verify_name="dne-verify-$dne_verify_nonce"
if docker volume inspect "$DNE_TEST_POSTGRES_VOLUME" >/dev/null 2>&1 || \
   docker container inspect "$dne_verify_name" >/dev/null 2>&1; then
  printf '%s\n' 'Recorded verification resources must be newly created.' >&2
  exit 1
fi
docker volume create \
  --label io.deepnative.verification-owner=gate \
  --label "io.deepnative.verification-claim=$DNE_TEST_POSTGRES_CLAIM" \
  "$DNE_TEST_POSTGRES_VOLUME"
dne_verify_container=$(docker run -d \
  --name "$dne_verify_name" \
  --label io.deepnative.verification-owner=gate \
  --label "io.deepnative.verification-claim=$DNE_TEST_POSTGRES_CLAIM" \
  -e POSTGRES_USER=dne -e POSTGRES_PASSWORD=local-preview-only -e POSTGRES_DB=dne_dev \
  -p 127.0.0.1:64329:5432 \
  --mount "type=volume,source=$DNE_TEST_POSTGRES_VOLUME,target=/var/lib/postgresql" \
  postgres:18-alpine@sha256:77f585114c32fbca283dc835b0596f4e52b51b4c6662d7810b2f4084f60a1873)
export DNE_TEST_POSTGRES_CONTAINER="$dne_verify_container"
export DNE_DATABASE_URL='postgresql://dne:local-preview-only@127.0.0.1:64329/dne_dev'
docker exec "$DNE_TEST_POSTGRES_CONTAINER" pg_isready -U dne -d dne_dev
# Proceed only after readiness and ownership/durability readback succeed.
make verify
# The same per-command environment must reach the ordinary, unbypassed pre-push hook.
```

Do not continue after a failed creation command or reuse an existing resource merely because its name/label matches. Keep the record for this verification campaign; a later run must preserve failures and must follow an actual source/environment remedy, not reset the instance to seek green. Read back `fsync`, `full_page_writes`, `checkpoint_timeout` and `checkpoint_completion_target`, and retain safe environment evidence. Never put a real hosting password, credentials or private member files in command arguments or reports; the displayed password is the existing disposable local fixture only.

Before creating restore resources, the restore adapter checks the explicit `DNE_TEST_POSTGRES_CONTAINER`, `DNE_TEST_POSTGRES_VOLUME` and `DNE_TEST_POSTGRES_CLAIM` together. It requires a full exact container ID, matching running pinned image, matching labels, only one published5432 binding at the exact127.0.0.1 fixture port, and the exact recorded writable local volume mounted at `/var/lib/postgresql`. Partial, malformed, mismatched or failed inspection refuses the rehearsal; it never falls back to shared Compose/host tooling. Actual binary pg_dump/pg_restore run through `docker exec -i` against that ID with the original limits. Without these options, exact54329 Compose/host validation is unchanged. All existing archive, corruption, manifest, privacy and cleanup assertions still run.

After verification, retain any failed fixture needed for diagnosis and its exact cleanup responsibility. A matching generated name alone is not ownership. Only when no gate/preview/session uses this instance, all databases created in the campaign have been ordinarily removed with actual absence confirmed, and the creation record and mount identities still match, orderly stop and remove **this recorded container**. Use `docker stop --timeout -1 "$DNE_TEST_POSTGRES_CONTAINER"` to wait for shutdown, then `docker rm "$DNE_TEST_POSTGRES_CONTAINER"`. Confirm no remaining container references the exact recorded volume before `docker volume rm "$DNE_TEST_POSTGRES_VOLUME"`. Do not force removal, prune by prefix or conceal a failed DROP by deleting the instance. Remove only these per-command environment options to return to the default fixture; no persistent Git, Docker or PostgreSQL configuration changes are required.
