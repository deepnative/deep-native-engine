# QA-279: integration unhandled-error signature checkpoint

The 27 September #302 delivery had a first-attempt `make verify` failure: the integration child exited 1 while Vitest JSON reported 98/98 assertion passes. The existing code-owned banners classified a Vitest unhandled error and excluded teardown/npm error banners. Its raw output was deliberately not retained. This narrows the likely failure path but does **not** identify the rejected value, originating module or root cause. Later clean local, pre-push, PR and main passes for #302 do not erase that failed attempt.

Vitest 5.0.1's JSON reporter reflects suite/test assertion results. Its independent unhandled-error stream can set a nonzero process exit after those assertions pass. The integration reporter now receives that stream through `onTestRunEnd` and writes only an allowlisted signature: kind, error class, selected transport/database code, named checked-in integration test (if known), and first-stack-frame category. It caps the recorded entries at three and never writes a message, raw stack, path, rejected value or child output. Unknown values become `other`. The verifier removes a prior report before a run, validates the new artifact against the fixed schema, copies only the validated categories into `application-verification.json`, and fails if a successful integration child did not produce a valid diagnostic artifact. Any nonzero child still fails even when all test assertions pass.

The shared verifier invokes `npm run test:integration` with ignored stdin, privately piped stdout/stderr and a 1 MiB buffer, generated loopback PostgreSQL database and isolated private-storage directory. It retains the parent database pool through the child and drops the generated database and storage in `finally`. The earlier direct diagnostic runs used fresh generated databases and exited 0; no comparison has reproduced the failure under direct or verifier invocation. The new signature is meant to distinguish a future test-owned rejection, application frame, dependency/network frame or runtime frame without crossing the #137 private-output boundary. It cannot establish the cause when Vitest does not report the error, when a frame is absent, or when several independent errors occur.

The focused unit tests use a synthetic private marker to prove no message, stack or arbitrary path enters the artifact, console or application report. The full repository gate tests the actual configured reporter with the real PostgreSQL integration suite and verifies a zero-error artifact on a successful run. On a future status-1 recurrence, retain `application-verification.json` and `integration-unhandled.json` after the artifact safety scan, compare the fixed signature with the test runner exit/signal/buffer/cleanup stage, then reproduce the implicated layer before changing behavior. A successful later run is negative evidence, not a repair. #279 remains open until a cause and evidence-supported fix are established.
