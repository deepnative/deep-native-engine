# CTP-011: synthetic entitlement ledger core, expiry and writeoff

This bounded slice implements an internal PostgreSQL accounting core for **synthetic test grants only**. It is not called by any route, offer, job or payment flow, and no live member can obtain or spend service units through it. The historical coaching allowances remain hypotheses. Foundation learning and local circle participation do not create ledger grants.

## Contract and boundaries

`syntheticLedger` accepts an explicit existing active member ID, one of five unit categories, a positive integer quantity, a caller-owned idempotency key and a required UTC validity window. Grants and new reservations require an active, unrevoked member. New reservations require the injected clock to be in the half-open interval `[startsAt, expiresAt)`. A grant holds its own available, reserved, consumed and expired balances. A reservation names one grant, so coach minutes cannot silently substitute for review minutes or study requests. Human categories count whole minutes; the two AI/practice categories count whole requests or sessions. Each operation appends an event with an exact-request fingerprint. The same key and request return the original ID; a changed request under that key fails. Different keys against one grant serialize through a PostgreSQL row lock, and the database checks that available + reserved + consumed + expired always equals the original grant quantity.

A reservation is settled in full, exactly once, by consume or release. Repeating the same settlement key is idempotent; a different settlement after the first is rejected. A caller explicitly invokes `expire` at or after the window end; it atomically moves unused available units to expired, stamps the grant and appends an idempotent expiry event. There is no automatic scheduler in this synthetic slice. An earlier reservation remains held through expiry and can be consumed. Releasing it at or after expiry moves the units to expired, even if the expiry operation has not yet run. Transactions roll back balance and reservation changes when event persistence fails. Database and connection errors are reduced to a fixed unavailable code, without raw SQL diagnostics. The event table rejects direct update/delete while its member exists; authorized member removal cascades the synthetic record. PostgreSQL schema and integration tests are the authority for race and rollback behavior. The unit tests cover validation, replay, failure mapping and operation paths.

An internal `adjust` operation supports only a **decrease** of currently available synthetic units before the grant expires. It never increases a grant, touches held or consumed units, changes the original quantity, or substitutes another category. The debited units move to a distinct nonnegative `adjusted` balance. The grant row lock serializes this writeoff against reservations and expiry, while an exact-key replay returns the original grant and a changed request conflicts. A failed event insert rolls the balance back. This models an invented fixture correction only: there is no staff API, correction authority, refund policy, positive adjustment or live grant.

This is an internal foundation for future approved entitlements, not an entitlement policy. No automatic grants or expiry job, policy-approved adjustment, annual reconciliation, funded minutes, review/support/AI settlement, staff booking, invoice, paid offer or browser journey are attached. Those areas remain on [CTP-011 #27](https://github.com/deepnative/deep-native-engine/issues/27) and its dependencies, particularly the foundation access decision in [#95](https://github.com/deepnative/deep-native-engine/issues/95). The synthetic deletion behavior must be re-evaluated against approved financial retention terms before live paid records exist.

## Verification and rollback

Behavioral checks cover three learner backgrounds without automatic grants, exact-key replay/conflict, cross-member denial, category separation, one-winner last-unit concurrency, consume/release, immutable event rows, member deletion, expiry boundary/race and forced event-write rollback. The clocked tests cover Jan 31 and leap-year February boundaries. Run `make verify` on the exact commit before pushing; the shared gate also runs the existing approved local browser matrix, provisional cases, production build and dependency scan. Full-MVP coverage remains separately outstanding.

The year-one integration fixture manually seeds only the historical **hypothesis** for a two-month pilot followed by ten continuation months. For Jan-31 anchors in ordinary and leap years it checks twelve contiguous half-open monthly windows, 36 category-specific grant events with exact-key replay, 720 coach minutes, 420 review minutes and 420 support minutes. It verifies that a future-month grant cannot be reserved at activation and that a changed same-key request conflicts. The pilot's one-time internal onboarding reserve is asserted separately and never appears as a second bookable grant. The CAD 3,000 plus CAD 9,000 amounts are planning inputs; the fixture makes no purchase, automatic grant, annual bundle or revenue claim. It does not prove a real continuation, qualified capacity, settlement, price approval or production billing policy.

The expiry change adds migration 017 and extends the internal ledger module. Migration 017 fails closed for preexisting synthetic grants with no window: it records an expiry event and expires their available balance while retaining reserved units for settlement. Migration 018 adds a zero-default adjusted balance and permits immutable adjustment events; it is idempotent on the existing synthetic schema. Before any real grants, rollback is to stop calling the module, remove its synthetic fixtures and revert the migration/module through a reviewed migration. Do not drop a table containing genuine financial records; a live retention and data-migration plan requires a separate owner decision.
