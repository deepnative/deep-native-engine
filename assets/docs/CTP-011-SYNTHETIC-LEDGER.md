# CTP-011: synthetic entitlement ledger core

This bounded slice implements an internal PostgreSQL accounting core for **synthetic test grants only**. It is not called by any route, offer, job or payment flow, and no live member can obtain or spend service units through it. The historical coaching allowances remain hypotheses. Foundation learning and local circle participation do not create ledger grants.

## Contract and boundaries

`syntheticLedger` accepts an explicit existing active member ID, one of five unit categories, a positive integer quantity and a caller-owned idempotency key. Grants and new reservations require an active, unrevoked member. A grant holds its own available, reserved and consumed balances. A reservation names one grant, so coach minutes cannot silently substitute for review minutes or study requests. Human categories count whole minutes; the two AI/practice categories count whole requests or sessions. Each operation appends an event with an exact-request fingerprint. The same key and request return the original ID; a changed request under that key fails. Different keys against one grant serialize through a PostgreSQL row lock, and the database checks that available + reserved + consumed always equals the original grant quantity.

A reservation is settled in full, exactly once, by consume or release. Repeating the same settlement key is idempotent; a different settlement after the first is rejected. Transactions roll back balance and reservation changes when event persistence fails. Database and connection errors are reduced to a fixed unavailable code, without raw SQL diagnostics. The event table rejects direct update/delete while its member exists; authorized member removal cascades the synthetic record. PostgreSQL schema and integration tests are the authority for race and rollback behavior. The unit tests cover validation, replay, failure mapping and operation paths.

This is an internal foundation for future approved entitlements, not an entitlement policy. No automatic grants, periods, expiry, adjustment, annual reconciliation, funded minutes, review/support/AI settlement, staff booking, invoice, paid offer or browser journey are attached. Those areas remain on [CTP-011 #27](https://github.com/deepnative/deep-native-engine/issues/27) and its dependencies, particularly the foundation access decision in [#95](https://github.com/deepnative/deep-native-engine/issues/95). The synthetic deletion behavior must be re-evaluated against approved financial retention terms before live paid records exist.

## Verification and rollback

Behavioral checks cover three learner backgrounds without automatic grants, exact-key replay/conflict, cross-member denial, category separation, one-winner last-unit concurrency, consume/release, immutable event rows, member deletion and forced event-write rollback. Run `make verify` on the exact commit before pushing; the shared gate also runs the existing approved local browser matrix, provisional cases, production build and dependency scan. Full-MVP coverage remains separately outstanding.

The change is isolated to migration 016 and the internal ledger module. Before any real grants, rollback is to stop calling the module, remove its synthetic fixtures and revert the migration/module through a reviewed migration. Do not drop a table containing genuine financial records; a live retention and data-migration plan requires a separate owner decision.
