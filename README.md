Deep Native Engine helps curious learners, IT practitioners and professionals in other fields learn to use AI in practical ways. You can start without coding or a career plan: choose a direction, try a small exercise and decide what to learn next.

[Try the GitHub Pages sample](https://deepnative.io/deep-native-engine/#sample-demo): choose a direction, practise with an invented brief, deliberately save a draft, self-check, and reload progress in the same browser tab. These simulated actions never change an account or call an AI provider. [Open the existing user portal](https://engine.deepnative.io/learn) for the separate Azure application and its saved sample work. See the [sample walkthrough and limits](assets/docs/PAGES-SAMPLE-DEMO.md).

Owner administration uses verified selected identities and deliberate finite entry; see [administrator access](assets/docs/ADMINISTRATOR-ACCESS.md). Legacy administrator credentials grant no authority.

## Developer setup

Your preview work is stored in local PostgreSQL and accessed through your browser session. Use it on your own computer with sample data.

Prerequisites: Node 24 (`.nvmrc`), Git, Make, Python 3.11+, Docker/Compose with a running daemon.

```sh
make setup
make verify
make dev
```

Open `http://127.0.0.1:3000`. Setup installs locked dependencies, Chromium, Firefox and WebKit for browser checks, the local database and the pre-push hook. It preserves an existing `.env`. Use focused checks while editing and making local commits. Finish edits and source review, commit, then run the full check once on the final clean revision intended for push; pre-push validates its original receipt. Review/handoff inspects that proof; merge verifies the actual source/tree/parents without another automatic full run. Changed combined source requires fresh verification. All tests run locally; GitHub Actions only deploys to Azure, with no PR/main test or proof-promotion run. Database and primary browser checks use configurable isolated parallel groups (`export DNE_TEST_GROUPS=4`, or memory-aware `auto`), with smaller memory/cache profiles documented in the verification guide. See [verification and troubleshooting](assets/docs/workflows/VERIFICATION.md). Agents should follow the [commit/push/merge testing strategy and dated performance evidence](assets/docs/workflows/LOCAL-VERIFICATION-PLAYBOOK.md#commit-push-and-merge-testing-strategy).

The Azure release targets [engine.deepnative.io](https://engine.deepnative.io) with durable PostgreSQL, private evidence storage and guarded deployments from locally verified `main`. The [Azure release guide](assets/docs/workflows/AZURE-DEMO-DEPLOYMENT.md) covers preservation, restart and rollback; [#45](https://github.com/deepnative/deep-native-engine/issues/45) records the actual deployed revision and public acceptance evidence. The hosted engine issues real CAD invoices (Deep Native Inc., paid offline by Interac e-Transfer) for courses and monthly coaching hours ([#624](https://github.com/deepnative/deep-native-engine/issues/624)); hosting does not activate external AI, card or bank payments, or qualified assessment. The first durable cutover requires verified preservation of the existing deployment; source/CI alone is not deployment proof.

On the hosted engine, members may enter real information on private learning forms; the local preview stays invented-only ([details](assets/docs/REAL-MEMBER-INPUT.md), #653). Email access is off by default. A hosted preview can set both `DNE_EMAIL_ENDPOINT` (the Azure Communication Services HTTPS endpoint) and `DNE_EMAIL_SENDER` (its authorized sender address). The application uses its explicitly selected Azure managed identity; it does not log links or fall back to a local outbox. A generic request acknowledgement is not a delivery receipt: a pending send can be lost on process restart, and the member can request a fresh link after the pending link expires in 15 minutes. Check inbox and spam before requesting again. Each request logs one content-free `member_email_request` line with its purpose and outcome (`sent`, `send_failed`, `invalid_address`, `already_bound`, `not_bound`, `member_unavailable`, `pending` or `rate_limited`), plus the provider error name and code for a failed send (#645). `sent` means Azure accepted the message, not that it reached an inbox; a work mailbox can still quarantine it. Configure the service, sender domain and minimum send permission separately, then verify actual delivery before presenting hosted email access as working. No existing member record or cookie is migrated automatically.

Assignment handoff is off by default. Set `DNE_ASSIGNMENT_HANDOFF=enabled` only in the intended runtime to accept a member’s own private assignment text and show the exact-version copy controls. Copies do not grant reviewer access or publish work. Disabling creation preserves existing copy inspection, export and deletion. The [assignment feedback guide](assets/docs/ASSIGNMENT-PRIVATE-FEEDBACK.md) describes consent, source-linked deletion and recovery. Every Azure release enables it on the hosted demo. Local tests and demonstrations use invented data.

Workflow feedback accepts your own private notes without an invented-data declaration. Saving a note neither requests moderator review nor shares it; review still needs a separate exact-version request and finite assignment.

Private support intake is off by default. `DNE_PRIVATE_SUPPORT_INTAKE=enabled` accepts a member's own private request without an invented-data attestation; sending has no charge or guaranteed response time. With existing staff entry and support assignment enabled, a current administrator discovers receipt/lifecycle metadata in the **Support intake inbox** and deliberately assigns a finite exact operator grant, or chooses **Answer this request myself** to answer it from their own administrator session until that session ends (shown and revocable in the request's assignment history). The operator or administrator separately acknowledges, keeps internal notes, sends visible replies and resolves; the member can reload replies, export or withdraw. If a request is outside what support currently covers, they can mark it **Outside current support**: the member sees that on their receipt, with no booking, price or completion promised. Disabling private intake preserves receipts and privacy controls. See the [private support guide](assets/docs/HOSTED-PRIVATE-SUPPORT.md); where no operator exists, a current administrator can answer requests themselves; no identity is provisioned automatically.

Verified owners can deliberately enter the [administrator console](assets/docs/ADMINISTRATOR-CONSOLE.md), find named learners with secondary exact account references, inspect enrollment/billing summaries and compose existing course proposals without exposing private writing. Disabled invoicing stays disabled.
